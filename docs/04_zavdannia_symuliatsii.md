# Завдання для симуляції

**Тема:** Мережа вузлів на MQTT з власним брокером
**Команда:** [ПІБ 1], [ПІБ 2], [ПІБ 3], [ПІБ 4]
**Дата вимірювань:** 09.11.2026

---

## 1. Мета симуляції

1. Перевірити, що мережа вузлів працює як ціле: телеметрія, автоматичне керування, тривоги,
   моніторинг, журнал.
2. Відтворити позаштатні ситуації: перегрів, аварійне зникнення вузла, тимчасова
   недоступність підписника.
3. Кількісно порівняти QoS 0/1/2 за доставкою, затримкою і пропускною здатністю.
4. Порівняти приватний брокер з публічними хмарними брокерами.

| Параметр | Значення |

## 3. Сценарій 1 — нормальна робота і перегрів

**Кроки:** `./run_demo.sh`, спостереження за панеллю.

**Результат.** Панель показує 4 вузли і контролер у статусі `online`, значення
оновлюються. Під час одного із запусків модель датчика згенерувала позаштатний сплеск на
кухні:

```
[controller] ALERT critical: перегрів у kitchen: 32.9°C
[fan-kitchen] power -> on (t=32.9°C)
```

Ланцюжок спрацював повністю: датчик → брокер → контролер (правило + тривога QoS 2) →
брокер → вентилятор → retained-стан → панель.

Дані логера за один сеанс (наскрізна затримка датчик → брокер → логер):

| Вузол | Записів | Середня затримка, мс | Макс. затримка, мс | T мін…макс, °C |
|---|---|---|---|---|
| t-bedroom | 23 | 2,33 | 8,66 | 21,0…22,6 |
| t-kitchen | 34 | 3,47 | 22,0 | 24,9…32,9 |

## 4. Сценарій 2 — аварійне зникнення вузла (LWT)

**Кроки:** запустити вузол `t-lab`, підписатися на його статус, завершити процес через
`kill -9` (імітація аварії: процес не встигає надіслати DISCONNECT).

**Результат:**
```
09:27:40 iot/home/lab/t-lab/status online
09:27:41 kill -9 вузла
09:27:41 iot/home/lab/t-lab/status offline      <- опубліковано брокером (LWT)
```

Брокер опублікував заповіт у ту ж секунду: ОС закрила TCP-з'єднання вбитого процесу, і
брокер одразу побачив обрив. Якщо пропаде живлення чи мережа (з'єднання не закривається
явно), обрив буде виявлено лише після 1,5 × keepalive = 15 с (keepalive = 10 с у
`config.connect`).

## 5. Сценарій 3 — QoS на приватному брокері

### 5.1. Реалістичне навантаження: 200 повідомлень, 50 повідомлень/с, payload 64 байти

| QoS | Отримано | Втрати | Дублікати | p50, мс | p95, мс | max, мс |
|---|---|---|---|---|---|---|
| 0 | 200 / 200 | 0 % | 0 | 0,89 | 1,00 | 40,0 |
| 1 | 200 / 200 | 0 % | 0 | 1,02 | 1,38 | 39,6 |
| 2 | 200 / 200 | 0 % | 0 | 20,36 | 22,41 | 40,0 |

### 5.2. Граничне навантаження: 1000 повідомлень без пауз

| QoS | Отримано | Швидкість публікації, повідомлень/с | p50, мс | p95, мс |
|---|---|---|---|---|
| 0 | 1000 / 1000 | 16 105 | 59,3 | 60,7 |
| 1 | 1000 / 1000 | 2 889 | 313,6 | 368,5 |
| 2 | 1000 / 1000 | 1 772 | 355,9 | 549,3 |

Під граничним навантаженням затримка вимірює насамперед час у черзі: видавець генерує
повідомлення швидше, ніж їх обробляє ланцюжок.

### 5.3. Офлайн-підписник (persistent session, 50 повідомлень)

| QoS | Отримано після повернення |
|---|---|
| 0 | 2–7 із 50 (у різних запусках) |
| 1 | **50 / 50** |
| 2 | **50 / 50** |

## 6. Сценарій 4 — приватний і публічні брокери

Умови: 200 повідомлень, 50 повідомлень/с; клієнти на тому ж ПК, брокери в Інтернеті.
«Приватний» — Mosquitto з п. 5.1.

| Брокер | QoS | Отримано | Втрати | p50, мс | p95, мс | max, мс |
|---|---|---|---|---|---|---|
| **приватний (localhost)** | 0 | 200 | 0 % | 0,89 | 1,00 | 40 |
| | 1 | 200 | 0 % | 1,02 | 1,38 | 40 |
| | 2 | 200 | 0 % | 20,4 | 22,4 | 40 |
| **broker.hivemq.com** | 0 | 200 | 0 % | 78,8 | 102,1 | 137 |
| | 1 | 200 | 0 % | 153,3 | 228,4 | 250 |
| | 2 | 200 | 0 % | 298,3 | 392,2 | 408 |
| **broker.emqx.io** | 0 | 40 | 80 % | 302,8 | 392,8 | 418 |
| | 1 | 40 | 80 % | 222,1 | 252,7 | 256 |
| | 2 | 70 | 65 % | 1 987,9 | 3 947,9 | 3 993 |
| **test.mosquitto.org** | — | — | — | брокер не надіслав CONNACK за 10 с (2 спроби) | | |

Офлайн-підписник на публічних брокерах: hivemq — QoS 0: 0/50, QoS 1: 50/50, QoS 2: 50/50;
emqx — QoS 0: 10/50, QoS 1: 50/50, QoS 2: 50/50.

**Пояснення до emqx.** У тесті втрачено від 65 до 80 % повідомлень навіть з QoS 1/2,
хоча видавець отримав підтвердження від брокера. Отже, брокер прийняв повідомлення, але не
переслав їх підписнику. Найімовірніша причина — обмеження частоти повідомлень на безкоштовному
публічному брокері. Окремо ми цю гіпотезу не перевіряли, але її підтверджує те, що в
офлайн-тесті (50 повідомлень одним пакетом) втрат на QoS 1/2 не було.

## 7. Аналіз результатів

1. **QoS 0 і QoS 1** на локальному брокері мають майже однакову затримку (~1 мс), а
   **QoS 2** — у ~20 разів більшу (20 мс). Причина — чотириетапне рукостискання
   (PUBLISH/PUBREC/PUBREL/PUBCOMP) з обох боків, від видавця до брокера і від брокера до
   підписника.
2. Пропускна здатність падає з ростом QoS: 16,1 тис. → 2,9 тис. → 1,8 тис. повідомлень/с
   (у 5,6 та 9 разів), бо кожне повідомлення потребує 1 / 2 / 4 пакетів і очікування підтверджень.
3. **Головна відмінність QoS — поведінка при недоступності отримувача.** Поки зв'язок
   стабільний, втрат немає навіть на QoS 0. Коли ж клієнт тимчасово офлайн, QoS 1/2
   гарантують 100 % доставки, а QoS 0 — ні.
4. На публічних брокерах затримка в 80–300 разів більша, ніж на локальному, і залежить від
   Інтернет-каналу. З ростом QoS вона зростає майже пропорційно кількості обмінів через мережу
   (hivemq: 79 → 153 → 298 мс, тобто ×1,9 і ×3,8).
5. Публічні брокери **ненадійні для експлуатації**: один був недоступний, інший втрачав
   більшість повідомлень. До того ж на них немає автентифікації: будь-хто, хто знає топік,
   може читати й підробляти дані.

## 8. Висновки та рекомендації

* Для **телеметрії** доцільно використовувати **QoS 0**: найменші накладні витрати, а
  втрата окремого виміру компенсується наступним.
* Для **команд і статусів** — **QoS 1** плюс ідемпотентна обробка на вузлі (повторна
  команда `on` нічого не ламає). Це дає гарантію доставки майже без зростання затримки.
* **QoS 2** — лише для рідкісних критичних подій (тривоги), де дублікат неприпустимий.
* Для виконавців і логера потрібна **persistent session**, інакше команди й дані на час
  перезапуску втрачаються.
* **Retained + LWT** дають актуальну картину стану мережі без додаткового опитування вузлів.
* **Публічний брокер** придатний лише для прототипування. Для реальної системи потрібен
  **приватний брокер** з паролями, ACL і TLS. У проєкті ця конфігурація реалізована
  (`mosquitto-secure.conf`) і перевірена.

## 9. Як відтворити

```bash
tools/bin/mosquitto -c broker/mosquitto-dev.conf &
.venv/bin/python -m experiments.compare_brokers --only local -n 200 --rate 50 --out results/local_50
.venv/bin/python -m experiments.compare_brokers --only local -n 1000 --rate 0 --out results/local_max
.venv/bin/python -m experiments.compare_brokers -n 200 --rate 50          # + публічні брокери
```

Сирі результати: `results/local_50/`, `results/local_max/`, `results/compare.*`.

> Примітка: у файлі `results/compare.md` рядки `local` отримано на запасному брокері amqtt
> (офлайн-тест QoS 1/2 там дав 0/50 — див. звіт «Середовище», п. 6). У таблиці п. 6 цього
> звіту для приватного брокера наведено дані Mosquitto з `results/local_50/`.
